API Backend Odontologia UPEA

API REST en Laravel 13 + Sanctum para el sistema odontologico de la Universidad Publica de El Alto. Cubre el flujo completo: Admision, Remision, Historia Clinica, Autorizacion Docente, Cajas, Insumos, Esterilizacion y Radiologia. Basado en las 16 tablas del sistema legado en PostgreSQL.

Laravel 13 Sanctum PostgreSQL 16 Auth completo Admin completo Modulos en progreso

1. Descripcion general

Backend desarrollado en Laravel 13 para gestionar la plataforma odontologica de la UPEA. La API REST usa Sanctum para autenticacion por token y un middleware personalizado (CheckRole) para validacion de roles.

Este documento cubre todos los modulos definidos en la nota interna CITE:/ODONT./Nº 172/2026 y en el informe de la Jefatura de Semiologia Estomatologica.

2. Objetivos del sistema

  • Que ningun paciente se pierda entre especialidades.
  • Seguimiento continuo y coordinado a traves de las diferentes especialidades.
  • Reemplazar las fichas fisicas por un registro digital confiable.
  • Acceso oportuno a los datos para brindar atencion de calidad.
  • Centralizar la informacion odontologica en un solo soporte tecnologico.
El sistema busca resolver: perdida de informacion, tiempos de espera, errores clinicos, dispersion de datos y modernizacion del proceso de atencion.

6. Flujo de atencion

El sistema acompana el flujo real de la clinica sin forzar a docentes ni estudiantes a adaptarse a una logica ajena.

1
Ingreso del paciente
El paciente ingresa por la Clinica de Admision, donde se registran sus datos personales y se llena la ficha de admision digital.
2
Derivacion a especialidad
Segun el caso, el paciente es derivado a la especialidad correspondiente (Ortodoncia, Endodoncia, Cirugia, etc.).
3
Aprobacion del docente y pago en Cajas
El docente aprueba el tratamiento propuesto por el estudiante. El paciente pasa por Cajas para cancelar el tratamiento.
4
Registro del avance
El docente registra paso a paso el avance del tratamiento en la historia clinica digital.
5
Autorizacion de insumos y esterilizacion
El registro de avance permite autorizar al area de Insumos la entrega de materiales y a Esterilizacion la entrega de paquetes.
6
Finalizacion del tratamiento
El estudiante finaliza el tratamiento y el docente lo registra como culminado. El Instituto de Investigacion puede acceder a informacion estadistica.

7. Autenticacion

Todas las rutas protegidas requieren el header Authorization: Bearer <token> y Accept: application/json.
POST /api/login Login ▼

Autentica un usuario por username y password.

Body

{
    "username": "admin",
    "password": "123"
}

Respuesta exitosa

{
    "success": true,
    "message": "Login exitoso.",
    "data": {
        "user": {
            "usernumber": 1,
            "username": "admin",
            "userfullname": "Administrador del Sistema",
            "usertype": "admin",
            "userdesc": "Acceso total"
        },
        "token": "1|xxxxxxxxxxxxxxxxxxxx",
        "token_type": "Bearer",
        "dashboard": { "route": "/dashboard/admin", "name": "Panel de Administracion" }
    }
}
POST /api/logout Cerrar sesion ▼

Revoca el token actual del usuario autenticado y registra el evento en logtable.

GET /api/me Usuario autenticado ▼

Devuelve la informacion del usuario autenticado segun el token Bearer, incluyendo sus especialidades activas.

11. Modulo Historia Clinica - /api/historia

El corazon del sistema. Gestiona el historial clinico completo del paciente a traves de las diferentes especialidades, permitiendo que un mismo paciente tenga historia en multiples especialidades vinculadas entre si.

GET /api/historia Listar historias ▼

Filtros: patientid, clinicalid, status, studentid, teacherid, authorized.

POST /api/historia Crear historia clinica ▼

Crea una nueva historia clinica vinculada a una remision existente.

Body

{
    "remissionid": 1,
    "admissionid": 1,
    "patientid": 1,
    "clinicalid": 1,
    "studentid": 4,
    "studentclinicalid": 1,
    "teacherid": 2,
    "teacherclinicalid": 1,
    "status": "Abierto"
}
GET /api/historia/{remissionid} Ver historia completa ▼

Devuelve la historia clinica con: paciente, admision, remision, tratamiento, insumos solicitados, esterilizaciones y radiografias vinculadas.

PUT /api/historia/{remissionid} Actualizar historia ▼

Actualiza el estado, el diagnostico, el pronostico o los tratamientos de la historia.

POST /api/historia/{remissionid}/archivo Subir archivo de historia ▼

Sube un archivo PDF o imagen de la historia clinica fisica escaneada. Se calcula un hash SHA-256 para integridad. Content-Type: multipart/form-data.

POST /api/historia/{remissionid}/revisar Revisar historia (docente) ▼

Body

{
    "reviewstatus": true,
    "reviewteacher": "OK",
    "reviewany": false
}
POST /api/historia/{remissionid}/autorizar Autorizar historia ▼

Autoriza la historia clinica (solo docentes responsables). Habilita el paso a Cajas.

POST /api/historia/{remissionid}/finalizar Finalizar tratamiento ▼

Registra la finalizacion del tratamiento. Cambia status a "Cerrado" y asigna endatetime.

23.3. Estructura de un controlador

<?php

namespace App\Http\Controllers\Api;

use App\Http\Controllers\Controller;
use App\Http\Requests\StorePatientRequest;
use App\Http\Resources\PatientResource;
use App\Models\Patient;
use App\Traits\ApiResponse;
use Illuminate\Http\JsonResponse;

class AdmisionController extends Controller
{
    use ApiResponse;

    public function index(): JsonResponse
    {
        $patients = Patient::query()
            ->when(request('search'), fn($q, $s) =>
                $q->where('patientci', 'like', "%{$s}%")
                  ->orWhere('patientname', 'like', "%{$s}%"))
            ->paginate(request('per_page', 15));

        return $this->success(PatientResource::collection($patients));
    }

    public function store(StorePatientRequest $request): JsonResponse
    {
        $patient = Patient::create($request->validated());

        return $this->success(
            new PatientResource($patient),
            'Paciente registrado correctamente.',
            201
        );
    }
}

24. Buenas practicas

24.1. Validacion siempre con Form Requests

Nunca validar en el controlador directamente. Crear un FormRequest por cada operacion. 

<?php

namespace App\Http\Requests;

use Illuminate\Foundation\Http\FormRequest;

class StorePatientRequest extends FormRequest
{
    public function authorize(): bool
    {
        return true; // la autorizacion la maneja el middleware CheckRole
    }

    public function rules(): array
    {
        return [
            'patientci' => ['required', 'string', 'max:50', 'unique:patienttable,patientci'],
            'patientname' => ['required', 'string', 'max:50'],
            'patientfatherlastname' => ['required', 'string', 'max:50'],
            'patientmotherlastname' => ['required', 'string', 'max:50'],
            'patientgender' => ['required', 'in:M,F'],
            'patientbirthdate' => ['required', 'integer'],
        ];
    }

    public function messages(): array
    {
        return [
            'patientci.required' => 'El CI del paciente es obligatorio.',
            'patientci.unique' => 'Ya existe un paciente con ese CI.',
            'patientname.required' => 'El nombre es obligatorio.',
        ];
    }
}

24.2. Usar transacciones en operaciones criticas

Cuando una operacion modifica varias tablas (ej: crear remision + historia clinica), envolver todo en una transaccion.

use Illuminate\Support\Facades\DB;

public function store(StoreRemissionRequest $request): JsonResponse
{
    return DB::transaction(function () use ($request) {
        $remission = Remission::create($request->validated());

        ClinicHistory::create([
            'remissionid' => $remission->remissionid,
            'admissionid' => $remission->admissionid,
            'patientid' => $remission->patientid,
            'clinicalid' => $remission->clinicalid,
            'status' => 'Abierto',
            'studentid' => $request->studentid,
            'studentclinicalid' => $request->clinicalid,
            'teacherid' => $request->teacherid,
            'teacherclinicalid' => $request->clinicalid,
        ]);

        return $this->success(new RemissionResource($remission), 'Remision creada.', 201);
    });
}

24.3. Registrar eventos en logtable

Toda operacion sensible (crear, actualizar, eliminar, login, logout) debe registrarse en logtable a traves del LogService. 

// En el controlador
$this->logService->record(
    type: 'create',
    data: ['model' => 'Patient', 'id' => $patient->patientid],

24.4. Usar Resources para las respuestas

Nunca devolver modelos Eloquent directamente. Usar JsonResource para controlar que campos se exponen.

<?php

namespace App\Http\Resources;

use Illuminate\Http\Resources\Json\JsonResource;

class PatientResource extends JsonResource
{
    public function toArray($request): array

            'patientgender' => $this->patientgender,
            'patientbirthdate' => $this->patientbirthdate,
            // NO exponer campos sensibles ni internos
        ];
    }
}

24.7. Manejo de archivos (historias clinicas)

public function uploadFile(Request $request, int $remissionid): JsonResponse
{
    $request->validate([
        'archivo' => ['required', 'file', 'mimes:pdf,jpg,jpeg,png', 'max:10240'],
    ]);

    $history = ClinicHistory::findOrFail($remissionid);
    $file = $request->file('archivo');
    $hash = hash_file('sha256', $file->getRealPath());

    $history->update([
        'inputfilename' => $file->getClientOriginalName(),
        'inputfile' => file_get_contents($file->getRealPath()),
        'inputfilehash' => $hash,
    ]);

    return $this->success(null, 'Archivo subido correctamente.');
}

25.1. Autenticacion con Sanctum

Todas las rutas excepto /api/login estan protegidas por auth:sanctum. El token se genera en el login y se revoca en el logout.

    Route::get('/me', [AuthController::class, 'me']);

        Route::get('/dashboard', [AdminController::class, 'dashboard']);

25.2. Middleware CheckRole

Valida que el usuario autenticado tenga uno de los roles permitidos antes de ejecutar el controlador.

<?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;

class CheckRole
{
    public function handle(Request $request, Closure $next, string ...$roles)
    {
        $user = $request->user();

        if (!$user || !in_array($user->usertype, $roles, true)) {
            return response()->json([
                'success' => false,
                'message' => 'No tiene permisos para acceder a este recurso.',
                'role' => $user?->usertype,
            ], 403);
        }

        return $next($request);
    }
}

25.3. Rate limiting

Proteger endpoints sensibles (login, subida de archivos) con limites de peticiones.

Rate::for('api', function (Request $request) {
    return Limit::perMinute(60)->by($request->user()?->usernumber ?: $request->ip());
});

Rate::for('login', function (Request $request) {
    return Limit::perMinute(5)->by($request->ip());
});

25.5. Proteccion contra ataques comunes

Ataque Mitigacion en Laravel
SQL Injection Eloquent / Query Builder con bindings
XSS Blade escapa por defecto, JSON responses no
CSRF No aplica para API token-based
Mass Assignment Usar $fillable o $guarded
Fuerza bruta Rate limiting en /api/login
Escalada de privilegios Middleware CheckRole en cada ruta
Exposicion de datos Usar Resources, no devolver modelos
Tokens robados Revocar tokens en logout, expiracion

25.6. Buenas practicas de seguridad

  • Usar HTTPS en produccion (forzar URL::forceScheme('https')).
  • Hashear passwords con Hash::make() (bcrypt por defecto).
  • No loggear informacion sensible (CI, diagnosticos).
  • Limitar el tamaño de archivos subidos (max:10240 = 10MB).
  • Validar MIME types de archivos (mimes:pdf,jpg,png).
  • Guardar archivos fuera de public/.
  • Usar env() solo en archivos de config, nunca en controladores.
  • Rotar APP_KEY si se compromete.
